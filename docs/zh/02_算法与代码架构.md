# 算法与代码架构

> 本文说明当前仓库中已经实现的 PIVOT、PIVOT-VOI 与 IMPROVE-X。英文 API
> docstring 和源码是行为依据；[theory notes](../theory_notes.md)、
> [estimands](../estimands.md) 和 [claim boundary](../claim_boundary.md) 保持原文；
> 本文不把计划中的适配器或未运行实验写成可用功能。

## 1. 总体数据流

项目把一次自我改进分成“生成候选、低成本评估、选择高保真查询、成对评估、记录和
审计”六步：

```text
incumbent Policy (pi_t)
        |
        v
ImprovementOperator A.propose(...)
        |
        v
CandidateBatch: tau_1 ... tau_K
        |
        +--> proxy / model: delta_proxy, footprint, response features
        |
        +--> acquisition: Random / Top Proxy / PIVOT / PIVOT-VOI
        |       |
        |       +--> selected IDs, HF budget, stop reason
        v
PairedEvaluator(world, mode=observer|actor|strategic)
        |
        v
transition rows + query ledger + metrics + manifest/hash
```

稳定公共入口在 `src/pivot_core/__init__.py`；历史研究代码仍位于 `src/pivot/`，
以避免破坏既有实验导入路径。IMPROVE-X 负责把“候选生成和多轮轨迹”标准化，PIVOT
负责“转移级验证和高保真预算分配”。

## 2. 核心数据结构

### 2.1 `Policy`

文件：`src/pivot/core/policy.py`。

`Policy` 是不可变参数映射：

- `parameters: Mapping[str, float>`：策略参数，必须非空、有限；
- `metadata: Mapping[str, str>`：算子、父策略等审计信息；
- `policy_id`：由规范化参数和 metadata 的 SHA-256 前 16 位生成；
- `action(state)`：受控环境使用的通用 action（`intensity + bias * state`，截断到
  `[-1,1]`）；
- `to_record/from_record`：JSON 友好的序列化，并校验内容派生的 ID。

策略 ID 是内容身份，不是运行序号。修改参数或 metadata 会生成不同 ID，便于追踪
“谁由谁改出”。

### 2.2 `PolicyTransition`

文件：`src/pivot/core/transition.py`。

一个 transition 固定 `incumbent`、`candidate`、`round_id`、`candidate_index` 和
`improvement_operator`，并携带所有世界层结果。重要字段分组如下：

| 分组 | 字段 |
| --- | --- |
| 身份 | `transition_id`, policy IDs, round/operator/index |
| proxy | `proxy_world_id`, `proxy_incumbent_value`, `proxy_candidate_value`, `delta_proxy` |
| actor | `actor_*`, `delta_actor`, `true_*`, `delta_true` |
| strategic | `strategic_*`, `delta_strategic`, `competition_strength`, `opponent_context` |
| 分解 | `mechanical_effect`, `competition_effect`, `improvement_reversal`, `strategic_improvement_reversal` |
| 足迹 | `update_footprint`, `footprint_components` |
| 可复现性 | `seed`, `paired_seed_ids`, `config_id`, `git_commit`, `timestamp` |
| 成本与决策 | `hf_queried`, `hf_query_reason`, `hf_query_cost`, `selected` |

`transition_id` 由 round、两个策略 ID、算子、候选索引、seed 和 config 派生。读取
记录时会重新计算并拒绝不一致的 ID，防止手工改行后仍被当作原始证据。

### 2.3 rollout 与配对结果

文件：`src/pivot/core/result.py`、`src/pivot/evaluation/paired.py`。

- `RolloutContext` 固定 `seed`、`scenario_id`、初始状态和外生值。
- `RolloutResult` 保存 value、环境步数、模拟器调用数、计算成本和 metadata。
- `PairedEvaluator` 对同一个 context 先跑 incumbent，再跑 candidate，计算每个 seed
  的差分 `candidate.value - incumbent.value`，然后给出均值、标准误、95% 置信区间、
  paired seed IDs 和成本。

成对设计共享随机性和初始条件，减少 common-mode noise。`UnpairedEvaluator` 在
`src/pivot/evaluation/unpaired.py` 中提供对照实现，要求 incumbent/candidate seed
集合不相交，只用于 paired/unpaired 消融。

## 3. 更新足迹和特征

文件：`src/pivot/footprint/generic.py`、`src/pivot/transfer/features.py`。

### 3.1 Generic footprint

```text
parameter_l2 = ||theta' - theta||_2
action_shift = mean_s |pi'(s) - pi(s)|
max_action_shift = max_s |pi'(s) - pi(s)|
mean_kl / max_kl = 0.5 * parameter_l2^2  (当前通用近似)
entropy_change
support_expansion
occupancy_divergence / trajectory_divergence = action_shift (当前代理分量)
episode_length_change = 0
```

返回值为 `Footprint(distance, components)`，其中当前标量距离是
`parameter_l2 + action_shift`。金融环境应使用专用 footprint（参与率、订单尺寸、
紧迫度、换手、流动性消耗、过价频率等），并保留组件列；不能只保留一个总分。

### 3.2 Differential model feature vector

`transition_feature_vector` 在 HF 查询前生成固定九维向量：

```text
[delta_proxy,
 update_footprint,
 response_strength,
 competition_strength,
 candidate_index,
 mean_kl,
 action_shift,
 entropy_change,
 support_expansion]
```

该函数明确不读取 `delta_true` 或 `delta_actor`，避免标签泄漏。`include_footprint=False`
把足迹五个分量置零，用于 footprint/no-footprint 消融。`policy_feature_vector` 和
`aligned_policy_features` 则服务于全局价值模型，和转移级校正模型分开。

## 4. PIVOT 基础算法

入口：`pivot_core.run_pivot_round`，实现：`src/pivot/algorithms/pivot.py`。

### 输入

- incumbent（可选 `Policy`）；
- `candidates`：mapping 或 `PolicyTransition` 序列；
- `proxy(candidate)`：返回 `delta_proxy`、footprint 等预查询字段的函数，可为 `None`；
- `hf(candidate)`：返回带 `delta_true`/`delta_actor` 的 mapping 或一个数值；
- `acquisition(rows, budget, ...)`：返回恰好 `budget` 个合法 transition ID。

### 执行步骤

1. `validate_budget` 检查预算位于零和候选数之间，并检查 candidate IDs 唯一。
2. 将 transition 序列转换为可变 row；运行 proxy，并默认 `hf_queried=False`。
3. 调用 acquisition 选出唯一合法 ID；返回数量不对或 ID 不在候选池会立即报错。
4. 对选中的 row 调用 HF；写入 `delta_true` 和查询成本，并把 `predicted_delta` 设为
   实际 HF 差分。`hf_query_reason` 由 transition 初始行或 HF 返回载荷提供时保留，
   round runner 不会替调用方虚构原因。
5. 未查询 row 保留模型预测（若 model 支持 `predict_correction`），否则回退到
   `delta_proxy`；不得静默标成真值。
6. 按 `predicted_delta` 选择本轮候选，计算 `update_selection_regret`（若所有候选
   均有真值）和 `cti_delta`。
7. 返回不可变 `RoundResult`：选中 ID、查询 ledger、完整 rows、预算、成本、acquisition
   名称/分数、停止原因和 posterior 版本。

### 选择策略接口

已有基线和获取器位于 `src/pivot/acquisition/`：

- `random.py`：随机 HF 查询；
- `top_proxy.py`：按 `delta_proxy` 查询或选择最高 proxy；
- `uncertainty.py`：按不确定性采样；
- `footprint.py`：最大足迹基线；
- `pivot.py`：传统转移级 PIVOT 获取；
- `pivot_voi.py`：PIVOT-VOI；
- `common.py`：ID 提取、数值读取和预算校验。

比较这些方法时必须冻结同一 candidate batch、相同 seed/环境和相同 HF budget；否则
选择差异可能来自候选生成或预算，而不是获取算法。

## 5. PIVOT-VOI

入口：`pivot_core.run_pivot_voi_round`；核心实现：`src/pivot/acquisition/pivot_voi.py`。

### 5.1 后验模型

`BayesianLinearDeltaPosterior` 对校正量建模：

```text
correction = Delta_* - Delta_proxy
correction | z ~ linear-Gaussian posterior
predicted_delta = delta_proxy + correction
```

`fit(features, corrections)` 使用共轭高斯线性回归；`condition` 用 rank-one 更新；
`predict`、`predictive_variance` 和 `sample_predictions` 提供均值、方差与后验抽样。
`predict_correction` 兼容 `run_pivot_round` 的模型协议，并返回
`predicted_delta`、标准差和近似 sign-change probability。

### 5.2 EVSI 获取分数

`score_pivot_voi` 对每个候选：

1. 从当前后验抽样，计算当前最优候选、当前期望简单遗憾（*expected simple regret*）
   和选择概率；
2. 假设查询该候选得到一组 fantasy correction；
3. 对每个 fantasy 进行后验 `condition`，重新抽样候选差分；
4. 计算查询后的平均遗憾；
5. 定义 `EVSI = max(0, current_regret - post_query_regret)`，再除以 `hf_query_cost`：

```text
acquisition = EVSI / cost
```

分数按 acquisition 降序、transition ID 升序稳定排序。`select_pivot_voi` 返回前
`budget` 个 ID。

### 5.3 停止规则

`should_stop` 使用预先指定的两个条件：

```text
selection_probability >= 1 - delta  -> stop, reason="selection_probability"
max_acquisition < eta                -> stop, reason="evsi_per_cost"
```

若已停止，`run_pivot_voi_round` 将 HF budget 设为 0，仍保留模型选择和停止原因；否则
最多消费 `max_budget`。这是启发式 EVSI/成本规则，不是校准的 Bayesian value of
information 证明，也不保证全局最优。

## 6. IMPROVE-X 平台

IMPROVE-X 是对多轮自我改进的薄层平台，入口为 `src/improve_x/__init__.py`。

### 6.1 算子与候选批次

接口 `ImprovementOperator.propose(incumbent, round_id, seed, **kwargs)` 返回
`CandidateBatch`。批次不可变，并强制：

- 所有 transition 共用 incumbent、round 和 operator；
- candidate policy IDs 唯一；
- 至少一个候选；
- metadata 记录父策略和其他生成信息。

当前可复现实例 `EvolutionaryMutation`（`src/improve_x/operators/evolutionary.py`）
对指定参数执行 seeded Gaussian mutation，按上下界截断；若边界导致重复 ID，则使用
确定性的内部值回退。生成与评估严格分离，算子本身不读取世界真值。

### 6.2 多轮轨迹

`ImprovementTrajectory`（`src/improve_x/core/trajectory.py`）是 append-only 轨迹：

- `append_round` 要求新批次 incumbent 等于当前 policy；
- 每个 candidate 必须有一条 evaluation；
- 保存 selected index、query cost 和每轮结果；
- `current_policy` 返回最后选中的 candidate；
- 暴露 `proxy_curve`、`actor_curve`、`strategic_curve`、`true_curve` 及累计改进；
- `to_records` 将 transition 与 evaluation 合并为行，保留 `selected` 和成本。

### 6.3 失败分类与层级指标

`src/improve_x/failures/taxonomy.py` 按优先级标记：

1. `strategic_failure`：actor 正、strategic 负；
2. `environment_response_failure`：proxy 正、actor 负；
3. `observer_failure`：proxy 负、actor 正；
4. `optimization_drift`：轨迹 proxy 上升但 true 下降；
5. `unknown`：关键层缺失；
6. `none`：未观察到上述失败。

`compute_layer_fidelity`（`src/improve_x/metrics/fidelity.py`）计算 observer/actor、
actor/strategic、observer/strategic 的符号一致率，并返回各自可比较样本数。

## 7. ImprovementBench 数据契约

文件：`src/improve_x/benchmark/dataset.py`、`src/improve_x/benchmark/tasks.py`。

每行是 schema `improvementbench-v1` 的 `ImprovementBenchRow`，至少包含：

```text
transition_id, round_id, incumbent_policy, candidate_policy,
improvement_operator, world_level,
proxy_delta, deployment_delta, actor_delta, strategic_delta,
proxy_value, deployment_value, update_footprint, environment_response,
failure_type, seed, candidate_index, metadata
```

`from_transition` 从标准 transition record 映射字段并调用 failure taxonomy；它优先使用
`delta_true` 作为 `deployment_delta`，只有 `delta_true` 缺失时才回退为 `delta_actor`。
因此发布 ImprovementBench 前，必须在源 transition record 中保留原始世界层字段，不能
把该回退后的部署列误读成可用的 `direct` 或战略反事实。
数据集写入：

- `transitions.jsonl`：逐行 transition 数据；
- `metadata.json`：schema、行数、创建时间、source commit；
- `manifest.json`：文件 SHA-256 和行数。

`validate` 必须在发布前运行。`tasks.py` 提供 sign、ranking、explanation 三种任务，
每种任务只在其所需字段存在时计分。

## 8. 可复现和审计要求

任何算法运行都应把以下信息写入 row、ledger 或 manifest：

- candidate batch 的 incumbent/candidate policy ID；
- round、operator、seed、scenario/context ID；
- proxy 与 HF 世界配置 ID；
- paired seed IDs、rollout 数、环境步数和 simulator calls；
- HF 查询原因、预算和实际成本；
- 当前 Git commit、配置版本和时间戳；
- 未查询候选的预测来源（proxy 或模型）；
- 原始行、失败行和被排除行，不能只保留汇总表。

验证函数 `src/pivot/validation.py` 可检查 manifest 文件存在性与 SHA-256，图表 bundle
也必须同时有 PNG 和源 CSV。发布证据的状态和允许表述见
`docs/zh/05_结果与证据边界.md`（如已生成）及 `docs/claim_boundary.md`。

## 9. 源码地图（接手时按此定位）

| 层 | 主要路径 | 责任 |
| --- | --- | --- |
| 稳定 facade | `src/pivot_core/__init__.py` | 下游统一导入的公共 API |
| 核心对象 | `src/pivot/core/` | Policy、Transition、Rollout、结果契约 |
| 评估 | `src/pivot/evaluation/` | paired/unpaired、差分分解、不确定性 |
| 获取 | `src/pivot/acquisition/` | PIVOT、VOI 与基线 |
| 足迹/特征 | `src/pivot/footprint/`, `src/pivot/transfer/` | 更新响应特征和校正模型 |
| 轨迹/算子 | `src/improve_x/core/`, `src/improve_x/operators/` | 多轮自我改进生成 |
| 基准 | `src/improve_x/benchmark/` | ImprovementBench schema 和任务 |
| 失败/指标 | `src/improve_x/failures/`, `src/improve_x/metrics/` | 失败标签和层级 fidelity |
| 受控环境 | `src/pivot/environments/`, `src/improve_x/controlled.py` | World 0/1/2 与受控评估 |
| 审计 | `src/pivot/validation.py`, `src/pivot/logging/` | manifest、transition store 和校验 |

接手开发时先通过 `pivot_core` 验证接口，再在 `pivot` 或 `improve_x` 下新增实现；
不要复制一套平行的 Policy/Transition 类型。新增 acquisition 必须返回唯一合法 ID，
新增 world 必须实现与 `PairedEvaluator` 兼容的 `evaluate(policy, context, mode=...)`，
或实现其兼容的无 `mode` 形式（evaluator 会在 `mode` 参数不被接受时回退）。

## 10. 当前未完成或不能默认承诺的部分

- PIVOT-VOI 的 posterior、fantasy 和 EVSI 是实现级启发式；需要匹配预算实验验证，
  不能仅凭代码声称优于 Top Proxy 或 Random HF。
- Strategic world 的 best response 不预设全局 Lipschitz；应报告经验敏感度和置信区间。
- 金融和外部代理适配器属于边界/后置实验，缺少确认性运行时不能写成通用结论。
- 任何 `null` counterfactual、`DEV`、`UNDERPOWERED`、`NOT_RUN`、`BLOCKED` 必须在
  row 和报告中原样保留。

下一步实验顺序、预算、统计和命令由 `docs/zh/03_实验设计与指标.md` 与
`docs/zh/04_运行手册.md` 统一规定；本文只定义算法行为和代码契约。
