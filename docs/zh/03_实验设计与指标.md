## 1. 实验总览与执行顺序

PIVOT 的科学单位是一次有向更新 `tau=(pi, pi')`。每一轮先由改进算子生成候选批次，
再用 proxy 取得低成本信号，最后在固定高保真（HF）预算下查询部分候选。实验必须按
以下顺序组织，后续阶段不能绕过前置数据契约：

| 阶段 | 研究问题 | 当前代码/配置 | 主要输出 |
| --- | --- | --- | --- |
| E1 | 是否存在 Improvement Reversal（IR） | 受控 P2/E2C 相关实现 | transition rows、IRR/IDE/ISC |
| E2 | response 强度与 update footprint 是否改变误差 | `experiments/v9/e2c_operator_shift.py`、`configs/v9/e2c.yaml` | `results/v9/e2c-*`、operator-shift summary |
| E3 | performative overoptimization 与闭环选择遗憾 | `e3c_closed_loop.py`、`configs/v9/e3c.yaml` | closed-loop、CISR/ISR、方法比较 |
| E4 | Global Fidelity 能否替代 Improvement Fidelity | `e4c_learned_ood.py`、`configs/v9/e4c.yaml` | OOD reports、local/global ISC 与 IDE |
| E5 | PIVOT 在固定 HF budget 下的效率 | `e5c_efficiency.py`、`configs/v9/e5c.yaml` | efficiency frontier、group metrics、CISR/CTI |
| E6 | 金融机械响应是否随 participation 改变 | `configs/finance/f0_f1.yaml`、`f2_participation.yaml` | F0/F1/F2 paired rows；参与率曲线 |
| E7 | 战略响应是否造成 Strategic Improvement Reversal | `e7c_strategic.py`、`configs/v9/e7c.yaml` | opponent-mode rows、SIRR、strategic effect |
| E8 | 竞争强度、对手数量和适应速度的影响 | `configs/sweeps/e8.yaml`、strategic configs | sensitivity/competition diagnostics |
| E9 | 多轮 self-improvement 闭环终点是否保持 | `configs/sweeps/e9.yaml`、V15 closed-loop path | trajectory、terminal assessment、CTI/CISR |

P0–P10 是实现计划中的准入控制；本表只描述科学顺序。任何新实验先补充配置、锁定
seed、输出 schema 和 gate，再执行结果采集。

## 2. 三个世界与金融层

每条 transition 至少区分以下世界层，缺失值保持 `null`：

| 世界 | 记号/字段 | 机制 | 可以回答 |
| --- | --- | --- | --- |
| World 0 / Observer | `delta_proxy` | 固定、便宜、不会被策略改变的 proxy | 更新在观察器中是否变好 |
| World 1 / Actor | `delta_actor` 或 `delta_true` | 部署策略改变环境后的机械响应 | 是否出现 IR；`proxy>0` 但 actor 为负 |
| World 2 / Strategic | `delta_strategic` | 对手或其他代理依据策略作出响应 | 是否出现 SIR；actor 为正但 strategic 为负 |

当环境支持反事实时记录 `delta_direct`（在 incumbent 环境中执行 candidate），并计算：

```text
mechanical_effect  = delta_actor - delta_direct
competition_effect = delta_strategic - delta_actor
```

这三个量是不同 estimand，不能互相填充。金融 F0/F1/F2 固定同一 transition，仅改变
participation `rho = agent trading volume / market volume`；F2 的 fill-only impact 语义
以 [`docs/experiments/public-finance-evidence-2026-08-19.md`](../experiments/public-finance-evidence-2026-08-19.md)
为准。

## 3. V9 受控实验矩阵

V9 confirmatory profile 默认 `30` 独立 seeds、每个 transition `16` rollouts、
`40` rounds、每轮 `8` candidates、bootstrap `10,000` 次；smoke/dev profile 只能做
工程检查。环境与关键网格如下：

| 实验 | 环境/机制 | 关键自变量 | 方法/预算 | 独立单位 |
| --- | --- | --- | --- | --- |
| E2C | `performative_control`（response 0.35/0.85）、`congestion_resource`（0.30/0.75）、`mpe2_frozen`（0） | operator family、shift level | transition-level；记录 density/weight | seed/trajectory |
| E3C | performative、congestion；MPE2 作为冻结外部 null | calibration split、HF budget=2、acquisition method | Proxy Only、Global Value、Random HF、Top Proxy、Uncertainty、Paired LUCB、Global-VOI、PIVOT-H、PIVOT-VOI、All-HF | seed/trajectory |
| E4C | 从 E2C rows 训练的 global/local 模型 | trajectory/environment/operator/response holdout | Bayesian linear、bootstrap ensemble；匹配 holdout | test seed/trajectory |
| E5C | performative、congestion | candidate count 4/8/16；HF budget 0/1/2/4/8/16 | 同 E3C 方法；固定候选组和预算 | seed × group |
| E7C/E8 | fixed、reactive、best response、gradient adaptive、RL evolutionary | adaptation strength 0.25/0.5/1.0、opponent count/rate/steps | strategic rows；SIRR 与 effect | opponent seed/trajectory |

V9 的历史确认性结果位于 `results/v9/*-confirmatory/`，每个目录必须有
`scientific_decision.json`、`manifest.json` 和相应 rows/summary。V9 的“确认性”只适用于
各自注册的受控机制和配置范围。

## 4. V15 现代代理确认性设计

V15 采用预结果冻结协议 `configs/v15/confirmatory.yaml` 和
`experiments/v15/confirmatory_lock.json`：

- `30` rounds、每轮 `4` candidates；两类 operator：`harness_skill_evolution` 和
  `mutation_self_edit`；每类 `30` trajectories（总计 60 个 operator trajectories）。
- 主 scaffold 为 mini-SWE-agent，Pi 是第二 scaffold 复现；候选 task family 为两类。
- 固定 paired sandbox、相同 task snapshot、container digest、初始 context、resource
  limits；候选 batch 必须冻结后再做 promotion 对比。
- HF budgets `[1, 2, 4]`；PIVOT acquisition 为 `EVSI_per_cost`，参数
  `delta=0.05`、`eta=0.01`；bootstrap 置信度 95%，抽样单位为
  `trajectory_or_task_cluster`。
- 主要指标：`task_success_under_fixed_budget`，转移指标为
  `delta_proxy`、`delta_actor`、`delta_strategic`、IDE、ISC、IRR、SIRR、ISR、CISR、CTI。
- 允许的 policy edit space：system prompt、agent loop、tool/search/test/context policy；
  禁止把 gate task、assessment task、candidate identity 或 hypothesis 传给 operator。

确认性运行必须使用锁定值，不能传 `--trajectories`、`--rounds`、`--candidates`、
`--task-limit`、`--agent-steps` 等覆盖参数；输出目录非空时 runner 必须拒绝覆盖。

## 5. 指标、分母与统计单位

对每条可比较 transition，`delta = candidate - incumbent`。符号平局由
`tau_sign=1e-9` 处理；`abs(delta_proxy) <= tau_mtr`（`1e-8`）时 MTR 为 `null`。

| 指标 | 定义 | 分母/统计口径 |
| --- | --- | --- |
| IDE | `mean(abs(delta_proxy - delta_true))` | 同时存在 proxy 与 true 的 rows |
| ISC | `P(sign(proxy)=sign(true))` | 排除任一侧为平局的 rows；另报 `n_comparable_signs` |
| IRR | `P(delta_true<0 | delta_proxy>0)` | 仅 proxy 正的 rows；另报正 proxy 数与 reversal 数 |
| SIRR | `P(delta_strategic<0 | delta_actor>0)` | 仅 actor 正且 strategic 非空的 rows |
| MTR | `mean(delta_true/delta_proxy)` | 只纳入 `abs(proxy)>tau_mtr` |
| ISR | 每轮 `max(true delta)-selected true delta` | 先在 round 内计算，再按独立组汇总 |
| CTI | `sum(selected true delta)` | 轨迹内累计，不能把 transition rows 当独立重复 |
| CISR | closed-loop 终点的 selection regret/transfer 差异 | paired trajectory/cluster |
| `mechanical_effect` | `delta_actor-delta_direct` | 仅同时有 actor、direct 的 rows |
| `competition_effect` | `delta_strategic-delta_actor` | 仅同时有 strategic、actor 的 rows |

受控注册聚合优先使用 paired bootstrap；独立 run 之间先按 run/trajectory 聚合，再做
cluster bootstrap。E4 的模型差异按注册 run 配对；E5 的 ISR/CTI 按相同 candidate group
配对；E6–E8 以注册 run 或 opponent seed 为独立单位。transition 行数不是独立样本数。
失败、丢弃、无效和缺失 rows 必须保留在 failure ledger，不能插补。

## 6. 基线、消融与公平性

标准基线为 `Proxy Only`、`Random HF`、`Top Proxy`、`Largest Footprint`、`Global Value
Model`、`Global Ranking Model`、`Uncertainty Sampling`、`Paired LUCB`、`Global-VOI`、
`PIVOT-H`、`PIVOT-VOI`、`All-HF Oracle`。All-HF 只作 oracle reference，不能作为同预算
acquisition 方法参与优越性结论。

注册消融覆盖：paired/unpaired、transition/global-value、footprint/no-footprint、
active/random、PIVOT/Top Proxy、small/large update、weak/strong response、F1/F2、
fixed/adaptive competitor、single/multiple response model、candidate count 和 HF budget。
每个 acquisition 方法必须看到同一 candidate-batch hash，HF 查询预算相等；冻结 candidate
batch 后再比较策略，避免候选池变化造成混淆。

## 7. Gate 与验收条件

Gate ledger 位于 [`docs/experiments/gates.md`](../experiments/gates.md)。标记通过至少需要：

1. run ID、配置 hash、seed 列表、HF budget 和 metric/CI 均可追溯；
2. 至少三个有效注册 run，且预注册指标的 CI 下界满足 gate 条件；
3. manifest、原始 rows、失败 ledger、汇总和 provenance hash 完整；
4. 受控 fixture pass 与外部有效性审查分开记录。

`Fixture Pass` 仅表示冻结配置下的注册判定通过；不自动升级为跨环境、真实市场或普适
优越性结论。V15 还必须通过 sealed-plane、终态审计、claim/language/number/reproducibility
审计，确认性运行才可改变 `NOT_RUN`/`UNDERPOWERED` 状态。

## 8. 文件与数据契约

- V9 transition：`transition_rows.jsonl.gz`；E4：`ood_reports.*`；E5：
  `group_metrics.jsonl.gz` 和 `efficiency_frontier.csv`；E7：`strategic_rows.jsonl.gz`。
- 注册 runner 的每个目录应有 `config.yaml`、`run_manifest.json`、`stdout.log`、
  `stderr.log` 与实验 artifacts；非空目录禁止覆盖。
- V15 canonical 表位于 `results/v15/canonical/`，包括 transitions、promotion、
  closed-loop、HF query 的 CSV/Parquet 及 manifest。阶段输出位于
  `results/v15/{dev-* | external-*}`。
- 每行应保存 policy/candidate identity、round/operator/seed/context、各 world delta、
  footprint、query decision、成本、git/config/hash 和终态字段。
